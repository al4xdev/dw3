# Status

Every game file of the EU disc (SLES-03936) rebuilds byte-identical from this repository, and all of the game's code
compiles from matching C (Psy-Q's libraries stay split assembly). The PC port, built from the same C, runs on Linux and
on Windows (cross-built): it boots the user's disc, plays the movies, the music and the effects, draws through a software
GPU or a hardware renderer, and saves to memory-card images that an emulator can also read. A launcher and the built-in
mods ([`LAUNCHER.md`](LAUNCHER.md) "Built-in mods") are done. An ARM build runs on Linux handhelds through PortMaster
(see the [`README`](../README.md)).

Issue numbers written `#NN` below are issues of the upstream repository
[gascarcella/dw2003recomp](https://github.com/gascarcella/dw2003recomp/issues); this repository has its own tracker.

## Decompilation
- **Byte-identical builds:** `scripts/build.sh --check` rebuilds `SLES_039.36`, the 19 tier-1 overlays, the two tier-2
  overlays (WFIGHTMN, WFIGHTTS) and all 293 `WSTAG###` stage files from scratch and checks each SHA-1.
- **Matched code:** see [`PROGRESS.md`](PROGRESS.md) (generated by `tools/progress.py --readme`; Psy-Q library code is
  excluded): 3,606 of 3,606 functions, 100%. No holdouts are left (no `INCLUDE_ASM` or `NON_MATCHING` in game code); the
  last 8 matched with the shapes of ReGame-Labs/dw3_decomp's C for the same functions, rewritten in our names
  ([`THIRD_PARTY.md`](THIRD_PARTY.md)).
- **10 forced matches** (11 `FAKE:` comments; `grep -rn "FAKE:" src`), allowed as an endgame step (DECISIONS).
- **39 `LOOP_BLOCK`/`LOOP_BARRIER` uses** (DECISIONS "LOOP_BLOCK"), by evidence class: A1 5, A2 6, B 14, C 14.
- These counts are `tools/hacks.py`'s (`--list`: each one). CI's `--check` fails when they differ from this page, and on
  game code that is not C: any `INCLUDE_ASM` or `NON_MATCHING`, a `LOOP_BLOCK` without its evidence comment, and so on.
- **Data:** split per object and in C, except crt0's `.sbss`, a FIELDSTG zero block with psylink padding, and STDWTITL's
  LIBPRESS data.
- **Names:** every function is named; the EXE's C uses no default name but `D_80056088` (libgte's sin table) and the
  overlay addresses it calls through `LATE_FUNC`. 197 `unk_` fields remain; the 15 the C touches are only written or
  read by getters nothing calls, the rest are never accessed (`tools/ref_names.py` lists the US decomp's candidates,
  `tools/renames.py` replays the rename lists `tools/renames/*.txt`; upstream #56). Stage 528's small per-actor arrays in
  FIELDSTG and the WSTAG stage scripts' data keep their `D_` names.

## Reference tests
`scripts/test.sh` runs every layer that the machine can run (`tests/README.md` has the details):
- **Layer 1, goldens:** the game's own functions called inside the emulator (PCSX-Redux, Lua-driven), 25 families:
  battle rules, the card game, game state, records, experience and digivolution, training, shops, encounters, the
  battle's event queue, enemy AI and spoils, sprites, the GTE, LIBGS's view (the battle camera), the GPU and MDEC.
  `tests/host/replay.py` replays them through the C compiled for the host; mismatches are in `tests/host/FINDINGS.md`.
- **Layer 2, replays:** pad scripts run from boot with per-checkpoint hashes. `new_game` (boot to the first field map)
  and `first_battle_save` (registration, the first battle, a save and reload, shops and menus) reach 14 of the 19
  tier-1 overlays. The SPU write traces (`tests/sound/`, [`SOUND.md`](SOUND.md)) belong to this layer.
- **Layer 3, formats and saves:** file table, text, stage table and flag-range checks; save round trips between the
  port and the emulator, and the emulator's load of a save the port made off an inn (the save-anywhere mod).
- **The port's tests:** both layer-2 scripts replayed in the port against the emulator's checkpoints (also at `-m32`
  and under ASan/UBSan), the sound replayed on the emulator's timeline, the SPU core's and XA decoder's unit goldens,
  the settings, the mods, the 60 Hz mode against the patched game in the emulator.
- **Not reached by any test:** STAGSLCT, SOUNDTST and SHOCKTST (debug overlays with no pad route), WFIGHTTS, CARDGAME
  (needs party Charisma 60) and STDGNAME (later in the story). `tools/coverage.py` reports which functions the tests run.

## PC port
The design is in [`PORT.md`](PORT.md); the reasons are in [`DECISIONS.md`](DECISIONS.md).
- **Boot and replay:** all 388 units compile for the host (`-m64 -Werror` gate in CI); the port boots the disc (SHA-1
  checked) and replays both layer-2 scripts with the emulator's checkpoints.
- **Software GPU:** the whole VRAM equals the emulator's at the checked points (new_game; the first battle's textures,
  `tests/port/vram.py`); LIBGS's battle camera and lights are equal to the PS1's to the bit. It is the default renderer.
- **Hardware renderer** (upstream #31): `--renderer gpu` draws through SDL_GPU on Vulkan (Direct3D 12 first on Windows,
  upstream #67), from a rasteriser of the software GPU's command stream into a VRAM of its own. At internal scale 1 it
  equals the software VRAM (all 715 gpu golden lists, every 10th vsync of both replays; NVIDIA and lavapipe);
  `--internal-scale 2..8` draws at N times the resolution. Without a usable device it falls back to the software path.
  The `gles` renderer used on handhelds is described in psxstack's `docs/RUNTIME.md`.
- **Sub-pixel precision** (upstream #68): psxstack's GTE shadow keeps the fractions RTPS cuts from the screen
  coordinates and finds them again for 98 % of the first battle's drawn polygon vertices (`tests/port/subpixel_jitter.py`).
  Above internal scale 1 the hardware renderer draws the 3D at those positions (`--subpixel on|off`, default on).
- **Present filters** (upstream #69): `none` (default), `sharp`, `scanlines`, `crt` and `smooth` (xBR level 2), each a
  shader pass in psxstack's present; `--filter`, `video.filter`, `video.crt`; GPU renderer only.
- **Widescreen battles** (upstream #71): the `widescreen` mod shows the battle 16:9 through the GPU renderer's wide
  canvas; everything else stays 4:3 (the field: upstream #78).
- **Texture replacement** (upstream #70, #77): `--dump-textures DIR` writes every texture the game samples as a PNG
  named by its key (134 keys in new_game, 1,728 in first_battle_save); `--texture-pack DIR` loads a pack that the
  hardware renderer draws instead. Packs are data mods in the settings directory's `mods/`
  ([`LAUNCHER.md`](LAUNCHER.md)).
- **Sound:** our own SPU core and LIBSND reproduce the emulator's SPU write traces exactly on its timeline
  ([`SOUND.md`](SOUND.md)); output through SDL3 or `--wav`. The movies use our MDEC and XA decoder.
- **Saves:** memory cards as `.mcd` images; saves move both ways between the port and the emulator.
- **Save states** (upstream #80): `--save-state WHEN:FILE` and `--load-state FILE` put the whole machine in a file of
  about 8 MB that the same binary resumes from; a run resumed at the first battle ends exactly as the straight replay
  (`tests/port/savestate.py`; [`PORT.md`](PORT.md) "Save states").
- **Debug channel and MCP server:** `dw2003 --debug SOCKET` lets a tool pause, step, press, read and write memory and
  take screenshots between two vsyncs; `psxstack/tools/mcp/` (registered by `.mcp.json`) is the MCP server over it
  (gate: `tests/port/debug.py`).
- **Platforms:** Linux x86_64, Linux ARM (handhelds, through PortMaster) and Windows x86_64, cross-built from Linux
  (`scripts/build_windows.sh`; upstream #37). Under Wine, headless, the game replays both layer-2 scripts with the Linux
  build's log, record and SPU trace byte for byte (`tests/port/run.py --exe build/port-win/dw2003.exe --wine`). The
  Windows zip has been run under Wine 11.17 and GE-Proton 10-25; it has not run on real Windows. macOS is not planned.
- **The port stack:** the runtime, the Psy-Q shim, the build (`psxstack_add_game()`), the launcher and the debug tools
  live in the [`psxstack`](../psxstack) submodule, pinned by commit (`.gitmodules`; its `docs/PORT.md`,
  `docs/RUNTIME.md`, `docs/LAUNCHER.md`). This repository keeps the game's side: `include/port.h`, `port/game/` (the
  adapter, the mods, the asm stand-ins), `port/mods/`, `tools/port_inputs.py`, `tools/port_inventory.py`,
  `tools/mcp_game.py` and `.mcp.json`.

## Launcher and mods
- **Launcher** (`psxstack/launcher/README.md`): Dear ImGui on SDL3. Handles the disc (with a SHA-1 check), Play,
  settings, controls (rebinding, hotkeys, chords) and the mods' pages. A headless self-test runs in CI. On handhelds the
  launcher is `handheld/Digimon World 3.sh` with a small menu (`handheld/README.md`).
- **Crash report** (psxstack's `docs/PORT.md` "Crash report"): the game writes one on a signal or a fatal stop; the launcher
  keeps the run's log and puts the report into its Copy text; the release carries the game's `.debug` file for
  `scripts/symbolize.py`. On Windows the report comes with a minidump (`tests/port/crash.py --wine`).
- **Mods:** the built-in mods and their settings are in [`LAUNCHER.md`](LAUNCHER.md) "Built-in mods". With mods off, the
  binary's logs, records and audio are unchanged.
- **Release:** `scripts/package_appimage.sh` builds the Linux AppImage and `scripts/package_windows.sh` the Windows zip
  (and its PDB symbols zip); a tag `vX.Y.Z` produces a draft release with both ([`RELEASE.md`](RELEASE.md)). The
  PortMaster package is built by `portmaster/make_release.sh` (`portmaster/PUBLISHING.md`).

## Infrastructure
- **CI** (`.github/workflows/ci.yml`) runs per area (game, port, launcher; `scripts/ci_areas.sh`) on pull requests and
  pushes to `main`, and skips docs-only changes. An `areas` job gates parallel jobs (`check`, `game`, `port`,
  `port-mods`, `launcher`, `windows`), each set up by `.github/actions/setup`. A deploy key adds the disc-dependent
  build and tests. See [`CONTRIBUTING.md`](CONTRIBUTING.md) for the checks and [`DECISIONS.md`](DECISIONS.md) "CI per
  area" for the design.
- **Worktrees:** local work happens in git worktrees (`scripts/worktree_init.sh` shares the main checkout's tools).
- **Emulator:** a pinned PCSX-Redux build runs headless (`scripts/check_emulator.sh`), with OpenBIOS or the retail BIOS.

## Known limitations
- The port's game timing differs from the emulator's at CD loads and boot (by a few frames), so sound is compared on
  the emulator's timeline instead of frame for frame.
- Skip dialogues does not cover the code-driven prompts of the card game and some other overlays.
- The port's `-m32` and sanitizer builds need system packages (`gcc-multilib`/`glibc-devel.i686`, `libasan`,
  `libubsan`); CI installs its own.
- Handheld limitations are in the [`README`](../README.md) and `portmaster/README.md`.
